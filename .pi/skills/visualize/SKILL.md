# Visualize

图片只有在它能表达文字表达不了的东西时才配得上位置——形状、结构、方向、关系、几何。这个 skill 产出一张这样的图，保证它**正确**（maker 渲染出来、亲眼看过后才交付），并把它放进讲义，好在 Obsidian 里内联渲染。

你是**创意指导**。你决定精确的想法，并把它精简到最少的承载元素。**maker 子代理**负责编写、渲染、视觉验证，然后返回结果。你把结果嵌进回复。

## 什么时候该可视化（什么时候不该）

这套教学系统是在学习者脑子里建一张**依赖图**——无条件真理在根，派生事实挂在上面。当一张图能让这个结构（或某个几何关系）**可见**时，它才有力。以下情况伸手要一张图：

- 想法是一个**结构或关系**：依赖、带部件和箭头的系统、流程/管道、交换序列、状态机、树/层级、对比、包含关系。
- 想法是**空间或几何的**：坐标几何、数轴、向量、函数形状、物理排布。

不要在一句话或一个方程已经能承载时可视化。一张只是把旁边那句话重述一遍的装饰图只会加噪音、多一个出错机会。拿不准时，别画——缺一张图比一张假图便宜。

## 选哪个 maker

从 `.pi/agents/` 发现两个 maker：

- **`mermaid-maker`** — 结构性/关系性视觉：依赖图、流程图、时序/状态/ER/类图、树、思维导图、时间线。这是默认选项，直接契合依赖图教学法。
- **`svg-maker`** — Mermaid 摆不出的空间/几何视觉：精确坐标、几何图形、数轴、向量、函数图像、自定义形状。

经验法则：*节点和边 / 关系* → mermaid-maker。*位置和形状 / 几何* → svg-maker。

## 认真给 brief：一个想法，最少元素

最常见的失败是**塞太多**——每个多余标签都让图更难读、也更难摆对。给 brief 前，砍到能承载想法的最少元素，并对每个元素问：*"删了它，想法还清楚吗？"* 清楚就删。

给 maker **概念**和**你想要的具体元素**——不是一个模糊的主题，也不是一长串清单。

- 坏：`"画一张讲 TCP 怎么工作的图"`
- 好：`"graph TD：顶部一个节点 'packet'；箭头向下到 'ordering' 和 'retransmit on loss'；两个箭头都汇入 'reliable stream'。不要标题。表达可靠性是从 packet 搭出来的，不是并列的。"`

保持想法完整，但信任 maker 的构图；如果你列了超过 ~5-7 个元素，先砍。

## 调用

用 `subagent` 工具派发 maker：

```
subagent({ agent: "mermaid-maker", task: "<你精简、具体的 brief>" })
```

```
subagent({ agent: "svg-maker", task: "<你精简、具体的 brief>" })
```

### mermaid-maker 的返回

它返回**已验证的 Mermaid 源码**：

````
RESULT:
```mermaid
<已验证源码>
```
````

你把这整段 ```mermaid 代码块原样放进讲义即可（Obsidian 和 Hugo 都原生渲染 Mermaid）。如果它返回 `RESULT: NONE`，说明这个 brief 做不出正确的图——简化或重新想，或判断这张图不值得画。

### svg-maker 的返回

它把 PNG 和 SVG 存进项目的 `viz/` 文件夹，并返回：

```
RESULT:
filename: viz-<slug>-<timestamp>.png
path: <绝对路径>
```

你用 Obsidian 的 wikilink 嵌入返回的 **filename**（不是完整路径）加显示宽度：

```
![[viz-<slug>-<timestamp>.png|500]]
```

（这要求 `viz/` 在 Obsidian vault 内。若你的项目不在 vault 里，把 `viz/` 软链进 vault，或把该图按相对路径引用。）

## 怎么保证正确

- maker **绝不会**返回一张它没**看过**的图，所以"渲染正常但内容是假的"会在到达学习者之前被抓住。
- mermaid-maker 用 mermaid.ink 把源码渲染成 PNG 再看；svg-maker 用 rsvg-convert 渲染再看。两者都会反复迭代到正确。

## 嵌入

把结果直接放进你的教学回复里。先用一句话引入这张图，然后让它自己承载想法——**不要**再把每个元素用散文复述一遍。
